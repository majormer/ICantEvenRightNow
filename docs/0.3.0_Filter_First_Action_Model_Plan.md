# 0.3.0 Plan: Filter-First Action Model

## 1. Why This Scope Change

User feedback indicates the primary value is not recommendation text. The core value is:

- filtering by player-meaningful attributes (expansion, type, bind semantics), and
- applying explicit actions to the filtered set safely.

This plan re-centers the addon around "filter -> select -> act" workflows.

## 2. Product Direction (Target Outcome)

Shift from recommendation-led UX to action-scope-led UX:

- Users choose an action scope first (source -> target).
- Users narrow with high-value filters.
- Users select rows (or page) and run the action.
- Rules, context, and capacity remain hard safety gates.

Recommendations become optional/de-emphasized metadata, then removable.

## 3. Core Principles (Non-Negotiable)

- Keep explicit user selection before any move/sell.
- Keep hard rule enforcement (`Protect`, `Ignore`, `Never Move`, `Never Sell`).
- Keep context checks (bank/vendor/combat).
- Keep capacity checks and clear blocked reasons.
- Preserve conservative defaults for destructive actions.

## 3.1 Decision Log (Locked for 0.3.0)

The following decisions are accepted for implementation unless explicitly revised:

1. Multi-select is supported across all filter dimensions, with simple defaults.
2. Filter state persists per tab (Move, Organize, Vendor), not globally.
3. Text matching is case-insensitive in 0.3.0.
4. Advanced include/exclude filters should be visible via active filter summary chips.
5. Rules are always enforced and surfaced clearly as protected/blocked rows.
6. Recommendations can be overridden by explicit player actions, but safety gates remain.

## 4. Functional Scope for 0.3.0

### 4.1 Shared Filter System Across Action Tabs

Implement one shared filter evaluator used by Move, Organize, and Vendor tabs, with independent filter state per tab.

Required high-value filters:

- Expansion:
  - Current
  - Older (not current)
  - Unknown
  - Specific expansion IDs
- Type / category:
  - Quest
  - Profession
  - Reagents
  - Consumables
  - BoE
  - WuE
  - Vendor Sellable
  - (retain All and other existing categories as needed)
- Bind:
  - BoE
  - WuE
  - Soulbound
  - Warbound
  - BoP / character-bound where detectable

### 4.1.1 Filter UX Model: Simple by Default, Advanced on Demand

To avoid overwhelming users while still enabling precise workflows:

- Default (collapsed) filter bar:
  - Expansion (single-select)
  - Type (single-select)
  - Bind (single-select, if enabled)
  - Search text (single box)
- Advanced toggle opens include/exclude builder:
  - Include group (AND across dimensions)
  - Exclude group (hard exclusions applied after include match)

Multi-select behavior:

- Single-select remains default for clarity and speed.
- Each dimension can be toggled into multi-select mode with compact chips.
- Multi-select within one dimension is OR logic.
- Across dimensions, logic remains AND.

Include/exclude semantics:

- Include rules define what may be shown/actioned.
- Exclude rules remove items even if include rules match.
- Exclude always wins.

Text matching support:

- Include name contains (optional)
- Exclude name contains (optional)
- Matching is case-insensitive.

Example expression:

- Include: Expansion in {Dragonflight}, Type in {Reagent}
- Exclude: Profession in {Alchemy}, Name contains "leaf"

This supports the workflow: "Include only Dragonflight reagents, exclude alchemy items and names containing leaf."

### 4.1.2 Rules Visibility and Filtering

Rules remain hard policy constraints and are never bypassed silently.

- Rows blocked by rules should still be visible with clear blocked labels.
- Add a quick toggle to hide blocked/protected rows when users want only actionable rows.
- Active rule blockers should appear in tooltip and row detail text.

### 4.2 Action Scope Model (Primary UX Driver)

Add an explicit action scope selector that defines source and destination intent.

Baseline scopes for 0.3.0:

- Bags -> Bank
- Bank -> Bags
- Bank -> Bank (reorganization)
- Bags -> Vendor (sell)
- Bank -> Bags -> Vendor (two-step helper via Vendor flow)

Bank destination target options for scope-driven moves:

- Auto (best target by current policy)
- Private Bank
- Reagent Bank
- Warband Bank

Action override policy:

- Players may explicitly act on non-recommended rows.
- Rules/context/capacity blockers still prevent execution.
- For high-risk batch actions, show a confirmation summary before execution.

### 4.3 Named Bank Tabs (Stretch / Phase 2)

Named tab targeting is valuable but API-sensitive. Plan as a follow-on once tab identity and slot mapping are verified stable across Retail contexts.

0.3.0 default:

- deliver storage-tier targeting first,
- add named-tab targeting after API discovery and diagnostics.

## 5. UX / Tab Changes

### 5.1 Summary

- Reword copy to emphasize "choose scope + filters".
- Keep scan controls and context/status cards.
- Add shortcuts into common scope presets.

### 5.2 Move

- Replace recommendation-forward language with scope-forward language.
- Keep `Dump` and `Recall` as presets or aliases to scope choices.
- Add destination bank target selector for banking actions.
- Keep default filter controls compact; reveal include/exclude controls behind an `Advanced Filters` toggle.
- Keep page-level selection tools (`Select Page`, `Clear`, action button).

### 5.3 Organize

- Reframe as `Bank -> Bank` action scope.
- Use same shared filters to constrain candidate rows.
- Keep blocked reasons and movable-only selection.

### 5.4 Vendor

- Add expansion/type/bind filters (currently missing parity).
- Add the same advanced include/exclude filter capability used by Move/Organize.
- Preserve conservative sell gating and `Never Sell` rule support.
- Keep context-sensitive action text (Recall Selected / Sell Selected / Process Selected).

Vendor policy for 0.3.0 and beyond:

- 0.3.0: keep conservative sell action eligibility.
- Post-0.3.0: add an explicit opt-in expanded sell mode with stronger warning and confirmation UX.

Vendor sellable category for filtering:

- Add a `Vendor Sellable` filter category defined as item sell price >= 1 copper.
- Preferred source is a direct API truth when available; fallback is `sellPrice > 0` from item data.
- This category controls visibility/filtering, while separate safety policy controls sell action eligibility.

### 5.5 Rules

- No major flow change.
- Clarify rules as policy overrides that apply to filter-driven actions.

### 5.6 Settings

- No major scope changes required for 0.3.0.

### 5.7 Context-Sensitive Auto Close

- If the addon panel is open and bank or vendor context closes, auto-close the panel (universal behavior).
- Rationale: action context changed and stale panel state can mislead users.
- Opening the console with neither bank nor vendor open is allowed.
- Once bank or vendor context is entered during that session, closing that context closes the panel.

### 5.8 Tab Interface and Layout Polish

The current tab row reads visually like a row of buttons rather than tabs. It also does not communicate whether a tab can currently do useful work.

Tab availability states:

- Summary: always available.
- Move: available for browsing scanned data, but bank-dependent actions should be marked unavailable when bank context is closed.
- Organize: bank-context tab; mark as unavailable when bank context is closed.
- Vendor: vendor-context tab for selling; mark as unavailable when vendor context is closed. Bank recall prep can remain visible, but the tab should clearly state when sell actions are unavailable.
- Rules: always available.
- Settings: always available.

Tab UX requirements:

- Active tab should visually connect to the content panel.
- Inactive tabs should be lower-emphasis than active tab.
- Context-unavailable tabs should remain clickable for explanation, but show a disabled/warning visual state and an inline reason inside the panel.
- Avoid bracketed tab text (`[Move]`) as the primary active-state indicator once visual styling is improved.

Layout cleanup requirements:

- Align list frames consistently across Move, Organize, and Vendor.
- Move tab rows should align with the main content/list region, not with the search box offset.
- Standardize spacing between help text, controls, filter rows, lists, and footers.
- Keep footer controls aligned consistently across action tabs.

Expected user benefit:

- Users can tell which workflows are currently valid at a glance.
- The UI reads more like a console with real tabs instead of unrelated buttons.
- The action lists feel intentional and easier to scan.

## 6. Recommendation System Strategy

### 6.1 0.3.0 Transition

- Keep `BuildDecision()` as the safety/policy computation hub.
- De-emphasize recommendation badges/text in row UI.
- Remove dependency on recommendation state in default workflows.

### 6.2 Post-0.3.0 Cleanup

- Optionally remove recommendation fields/constants if no longer needed for sorting/tooltips.
- Keep blocked-reason diagnostics intact.

## 7. Technical Implementation Plan (Phased)

### Phase A: Foundation (Low-Medium Risk)

1. Create shared filter evaluation helpers used by Move/Organize/Vendor.
2. Normalize filter state shape in DB so all tabs read/write consistent fields.
3. Add missing filter controls to Vendor and wire to shared filtering.
4. Add advanced include/exclude evaluation (`include` then `exclude`) with deterministic ordering.
5. Ensure no action path depends on recommendation-only toggles.
6. Add active-filter summary chips (including advanced filters) for visibility.

Deliverable:

- Filter parity across tabs with existing behavior preserved.

### Phase B: Scope-First Actions (Medium Risk)

1. Introduce action scope enum and UI selector.
2. Map legacy `Dump to Bank` / `Recall from Bank` modes to scope presets.
3. Add bank target selector (`Auto`, `Private`, `Reagent`, `Warband`) for banking scopes.
4. Update action executors to honor explicit target when provided.
5. Add confirmation prompt for high-risk batch operations.

Deliverable:

- Players can intentionally move filtered sets between storage scopes without recommendation friction.

### Phase C: Tab and Layout Polish (Low-Medium Risk)

1. Add tab availability evaluation based on current context.
2. Add visual states for active, inactive, and context-unavailable tabs.
3. Add inline context messages for unavailable tabs.
4. Rework tab styling so active tabs visually attach to the content panel.
5. Normalize list and footer alignment across Move, Organize, and Vendor.

Deliverable:

- Tabs communicate availability, and action tab layouts align consistently.

### Phase D: UX Copy + Diagnostics (Low Risk)

1. Update labels/help text to filter-first language.
2. Improve empty states to explain whether no rows are due to:
  - scan data missing,
  - filter mismatch,
  - context gate,
  - capacity/rule block.
3. Keep tooltips focused on "why blocked" and "what action will happen".
4. Label rule-blocked rows clearly and provide actionable-only view toggles.

Deliverable:

- Reduced confusion and faster operation for high-frequency workflows.

### Phase E: Scan Automation and Context Refresh (Low-Medium Risk)

Reduce user scan burden by triggering scans automatically at key moments:

1. On opening the console, perform `ScanInventory("all", true)` when context permits.
2. On switching tabs, trigger a quiet rescan when entering action tabs.
3. After action execution (move/organize/vendor), keep scheduled rescan behavior and ensure immediate refresh.
4. Keep bank/vendor context checks so scans degrade safely when interaction frames are not open.

Deliverable:

- Users no longer need manual scan buttons for normal workflows.

### Phase F: Named Bank Tab Targeting (Optional / Later)

1. Add diagnostics for available tab IDs and slot ranges.
2. Validate behavior with account bank states and API variance.
3. Add named-tab selector only after stable mapping exists.

Deliverable:

- Explicit tab-level routing when technically safe.

### Phase G: Expanded Vendor Sell Mode (Optional / Later)

1. Introduce opt-in toggle for expanded sell eligibility.
2. Require a warning modal that clearly states risk and scope.
3. Require confirmation summary with selected row count and total vendor value.
4. Keep all rule/context/combat/capacity guards unchanged.

Deliverable:

- Advanced users can intentionally broaden sell actions with explicit consent and safeguards.

## 8. Data Model and Compatibility Notes

Planned DB additions (names provisional):

- `ui.actionScope`
- `ui.bankTargetScope` (`Auto|Private|Reagent|Warband`)
- Per-tab filter storage keys (example):
  - `ui.tabFilters.Move`
  - `ui.tabFilters.Organize`
  - `ui.tabFilters.Vendor`
- Each per-tab filter object uses the same shape:
  - `filters.expansion.include` (single or multi)
  - `filters.type.include` (single or multi)
  - `filters.bind.include` (single or multi)
  - `filters.profession.exclude` (optional multi)
  - `filters.name.includeText` (optional)
  - `filters.name.excludeText` (optional)
  - `filters.hideBlocked` (boolean)
  - `filters.advancedEnabled` (boolean)

Compatibility:

- Migrate existing `ui.mode` to default `actionScope` values on load.
- Preserve old fields during 0.3.0 for backward compatibility.

## 9. Acceptance Criteria

### 9.1 Core Workflow Acceptance

1. User can choose an action scope, apply filters, select rows, and execute.
2. Works for:
   - Bags -> Bank
   - Bank -> Bags
   - Bank -> Bank
   - Vendor processing with filter controls
3. Rules/context/capacity blocks are still enforced.

### 9.2 Example User Stories

1. "Move all Dragonflight quest items to inventory":
   - Scope Bank -> Bags
   - Expansion = Dragonflight
   - Type = Quest
   - Select page/rows and Recall.
2. "Bank all old consumables from bags into reagent or warband depending on target":
   - Scope Bags -> Bank
   - Expansion = Older
   - Type = Consumable
   - Target = chosen bank storage.
3. "Sell filtered old consumables safely":
   - Vendor tab with Expansion/Type filters
   - Explicit selection required
   - `Never Sell` still blocks.
4. "Include Dragonflight reagents, exclude alchemy and names containing leaf":
   - Expansion include = Dragonflight
   - Type include = Reagent
   - Profession exclude = Alchemy
   - Name exclude text = `leaf`
   - Select rows and run scope action.
5. "Show me everything vendor-sellable, then I decide":
   - Vendor tab
   - Type or category includes `Vendor Sellable`
   - Optional excludes for protected terms
   - Explicit selection and confirmation before sell run.

## 10. Risks and Mitigations

- Risk: Regressions from touching shared Core.lua flow.
  - Mitigation: implement in small phases, preserve function boundaries, and validate each action path.
- Risk: Bank API variance (especially named tabs).
  - Mitigation: defer named-tab shipping until diagnostics prove stable mapping.
- Risk: User confusion during transition from recommendations.
  - Mitigation: copy updates and temporary compatibility aliases (`Dump/Recall` as scope presets).
- Risk: Advanced filters become invisible state.
  - Mitigation: active filter chips + one-click clear + per-tab filter summary.
- Risk: Auto scan adds unnecessary load.
  - Mitigation: quiet scans with context gating and throttled timing.
- Risk: Vendor power features increase accidental sell anxiety.
  - Mitigation: strict rule blocks + visible blockers + confirmation summaries.
- Risk: Context-unavailable tabs feel broken if disabled too aggressively.
  - Mitigation: keep them clickable, show clear inline context messages, and only block unsafe actions.
- Risk: Custom tab styling fights WoW stock UI constraints.
  - Mitigation: use conservative texture/backdrop/font changes and validate in-game at multiple UI scales.

## 12. First-Pass Implementation Defaults

These defaults remove implementation blockers and can be revised after in-game testing:

1. Confirmation prompts:
  - Always confirm vendor sell actions.
  - Confirm non-vendor batch actions at 20+ selected rows.
  - Expanded vendor mode later gets stronger confirmation regardless of row count.
2. `recommendedOnly`:
  - Soft-deprecate in 0.3.0.
  - Keep the saved variable for compatibility.
  - Hide or de-emphasize the control in the primary UX.
3. Bank target default:
  - Default to `Auto`.
  - Remember the last selected bank target per action tab/scope after the user changes it.
